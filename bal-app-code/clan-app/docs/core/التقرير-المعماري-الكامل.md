## القسم الثالث — هل البنية تسمح بالملء التلقائي الكامل؟

**الرؤية المطلوبة**: AI ينشئ اسم الحلم + الوصف + القمة + المراحل + اسم/وصف كل مرحلة + نسبة الإنجاز + مدة المرحلة + المهام اليومية.

| الحقل المطلوب | موجود في البنية؟ | الدليل |
|---------------|------------------|--------|
| اسم الحلم | ✅ | `POST /goals/dream {title}` (controller:143) |
| وصف الحلم | ⚠️ جزئي | `Goal.description` موجود (schema:887) لكن **لم يُملأ أبداً** — generatePlan لا يرجع وصفاً |
| القمة النهائية | ✅ | آخر خطوة = القمة (PLAN_SYSTEM: «الخطوة الأخيرة هي الهدف النهائي») |
| اسم كل مرحلة | ✅ | `GoalStep.title` من JSON الخطة (controller:227) |
| وصف كل مرحلة | ✅ | `GoalStep.description` من JSON الخطة |
| نسبة الإنجاز | ⚠️ محسوبة لا مخزنة | تُحسب لحظياً في `complete` رد (progress.completed/total) — **لا تُخزن ولا تُرجع من أي GET** |
| مدة المرحلة | ❌ غير موجود | `GoalStep` بلا حقل duration/estimatedMin |
| المهام اليومية المقترحة | ❌ غير موجود | لا توليد مهام من الخطة (صفر كود) |

**الخلاصة: البنية تسمح بـ 4 من 8 — النواقص: وصف الحلم، مدة المرحلة، المهام اليومية، استرجاع التقدم.**

## القسم الرابع — أفضل آلية للملء التلقائي

| الخيار | التقييم |
|--------|---------|
| A: AI يعيد JSON منظم | ✅ **هو المطبق فعلياً** — PLAN_SYSTEM يطلب `{"steps":[{title,description}]}` ويُخزن مباشرة (الخيار الموجود والمختبر: dream-flow 17/17) |
| B: AI ينشئ Goal+GoalStep مباشرة | ❌ خطير: كتابة مباشرة بلا مراجعة بشرية — يكسر «موافقة المستخدم» في الرؤية |
| C: Draft → موافقة → حفظ | ✅ **مطبق أيضاً** (draft=true → approve) — يتوافق مع الرؤية تماماً |
| D: بنية أفضل موجودة | ⚠️ التحسين الوحيد الممكن: توسيع الـ JSON ليشمل الحقول الناقصة (وصف/مدة/مهام مقترحة) على نفس آلية draft→approve |

**الاختيار الأنسب: C+A مدمجين (كما هو مطبق) مع توسيع JSON الخطة بالحقول الناقصة — الآلية صحيحة، النموذج ناقص.**

## القسم السابع — التقرير النهائي

### ✅ ما يعمل حالياً (مُثبت حياً)
1. كويز Gemini حقيقي + خطة 5-7 خطوات JSON + حفظ تلقائي على المسودة
2. موافقة → Goal نشط + أسبوع أول تلقائي
3. تسلق بالترتيب الصارم (400/409/404) + إتمام القمة يكمّل الهدف (`completedAt`)
4. التوثيق الأسبوعي (6 أسئلة + مخصصة + قفل) مرتبط بـ GoalWeek
5. عزل الملكية الكامل (IDOR محمي — 404)
6. الاختبار الحي: dream-flow 17/17 ✅

### ⚠️ ما يحتاج ربط
1. AI Context: إضافة خطوات الهدف + المرحلة الحالية + التقدم (completed/total) لسياق المحادثة
2. إتمام الخطوة: Sparks + أحداث Analytics + إشعار/احتفال
3. المهام: رابط goalId/stepId + توليد مهام أسبوعية من الخطة
4. Focus: رابط اختياري بالخطوة الحالية
5. Achievements: مقياس GOAL جديد
6. Analytics: عدّادات تقدم الخطوات

### ❌ ما لا يحقق الرؤية
1. لا توليد مهام من خطة الجبل (الخطوة 9 من الرحلة)
2. لا تقدم الجبل في Analytics (الخطوة 12)
3. لا تقدم الجبل في ذاكرة AI (الخطوة 13)
4. لا مدة لكل مرحلة · لا وصف للحلم · لا استرجاع خطوات بعد إعادة الفتح
5. لا فرونت أصلاً (لا شاشة جبل في أي تطبيق)

### 🟢 أفضل Source of Truth
**Prisma Goal + GoalStep (PostgreSQL)** — بنية سليمة (فهارس، ترتيب صارم، Cascade) — هي الأساس الصحيح، والفرونت يجب أن يقرأ منها دائماً عبر API واحد يجمع: goal + steps + progress + openWeek.

### 🟢 أفضل آلية للملء التلقائي
**الآلية الحالية C+A (Draft → JSON من Gemini → موافقة → حفظ)** — صحيحة ومختبرة — تحتاج فقط توسيع الـ JSON بالحقول الناقصة (وصف الحلم، مدة المرحلة، مهام مقترحة لكل مرحلة) ونفس تدفق الموافقة.

### 🟢 أفضل رحلة مستخدم
1-8 تعمل بالباك وتنتظر الفرونت — 9-13 تتطلب الربط المذكور أعلاه.

### 🟢 هل الجبل جزء من النظام أم شاشة مستقلة؟
**ما زال شاشة مستقلة (جُزُر):** الجبل نفسه (Goal+GoalStep+Weeks) نظام أصيل ومحمي — لكنه **غير موصول** بالمهام والتركيز والتحليلات والإنجازات والإشعارات وذاكرة الـ AI، وليس له أي واجهة.

### 🟢 هل النظام كله يعمل كجسد واحد؟
**لا.** المنصة تعمل كثلاث جزر: (1) إنتاجية يومية (مهام/تركيز/منبه/نقاط) · (2) جبل الأحلام (هدف/خطوات/أسابيع) · (3) تواصل (عشائر/رسائل/ألعاب) — الجبل متصل بالتوثيق فقط، والتوثيق متصل بالتحليلات جزئياً. الربط المفقود الرئيسي: **المهام ↔ الخطوات ↔ التقدم ↔ AI**.
