## 1. ملخص ما تم إنجازه وإصلاحه

تم بنجاح إغلاق **الثغرة رقم 3 (حماية مخرج المقاييس `/metrics`)** وتأمينها على السيرفر الحي:
* **الملفات المعدلة**: `src/config/env.js`، `src/app.js`، `.env`، `.env.example`.
* **آلية الحماية المطبقة**:
  * إلزام تقديم توكن سري في الترويسة `x-metrics-token` أو `Authorization: Bearer <TOKEN>`.
  * حجب الوصول العام تماماً برمز `403 Forbidden` عند غياب التوكن أو خطأه.
  * في بيئة الإنتاج (`NODE_ENV=production`) يتم الرد بـ `404 Not Found` الصامت إذا لم يتم ضبط التوكن، لمنع الاستطلاع الخارجي لبنية المسارات وسجلات الـ Latency.
  * تم اختبارها حياً بـ `curl` وتأكد نجاح الإغلاق بنسبة 100%.

## 2. الثغرة الأولى: ربط بوابات الدفع الحقيقية واستقبال الـ Webhooks

### طبيعة الثغرة والفجوة الحالية:
* **المشكلة**: المنظومة تحتوي على منطق متكامل لتحويل الإحالة من المستوى الأول (التسجيل المجاني) إلى المستوى الثاني (الاشتراك المدفوع) عبر دالة `processPaidReferralConversion` في `src/services/referral.service.js` والتي تمنح الداعي **+150 شرارة كبرى و20 رسالة ذكاء اصطناعي**.
* **الفجوة**: لا يوجد حتى الآن مسار Webhook عام يستقبل إشعارات الدفع الحقيقية من بوابات الدفع (مثل **Paymob** للسوق العربي أو **Stripe** عالمياً) للتحقق من التوقيع الرقمي (HMAC Signature) وتحديث جدول `Subscription` وتفعيل مكافأة الداعي تلقائياً فور نجاح عملية السداد.

```
[ العميل يدفع في التطبيق ] 
         │
         ▼
[ بوابة الدفع: Paymob / Stripe ] 
         │  (Webhook مشفر بـ HMAC)
         ▼
[ مسار الـ Webhook المفقود: POST /api/payments/webhook ] ──> ⚠️ الفجوة الحالية
         │
         ├─► تفعيل Subscription للمستخدم
         └─► استدعاء processPaidReferralConversion(userId, tx)
```

### خطة المعالجة الهندسية عند التنفيذ:
1. **إنشاء مسار الـ Webhook**:
   * إضافة `POST /api/payments/webhook` بـ `express.raw({ type: 'application/json' })` للتحقق من التوقيع الرقمي الصارم قبل قراءة الجسم.
2. **التحقق من التوقيع الرقمي (HMAC Verification)**:
   ```javascript
   const calculatedHmac = crypto
     .createHmac('sha256', env.paymobHmacSecret)
     .update(rawBody)
     .digest('hex');
   if (calculatedHmac !== req.headers['x-paymob-signature']) {
     throw forbidden('توقيع الدفع الرقمي غير مطابق');
   }
   ```
3. **التحديث الذري في قاعدة البيانات**:
   * إنشاء سجل في جدول `Payment`.
   * تفعيل أو تجديد باقة `Subscription` (`BASIC`, `PRO`, `HIGH`).
   * تشغيل `processPaidReferralConversion` ذرياً داخل نفس المعاملة لمنح الداعي نقاطه ورسائل الـ AI.

## 3. الثغرة الثانية: معمارية معدل الطلبات وعزل المستويات (Rate-Limit Architecture)

### طبيعة الثغرة والفجوة الحالية:
* **المشكلة**: الـ Rate Limiter المطبق حالياً في `src/app.js` يعتمد على الـ IP (`127.0.0.1` أو IP العميل المشترك) بسقف `100 طلب / 15 دقيقة` في وضع التطوير.
* **الخلل الناجم**:
  1. إذا كان مئات المستخدمين خلف NAT واحد (مثل شبكة جامعة أو شركة أو مشغل محمول)، فإن تجاوز أحدهم للحد يحظر جميع المستخدمين على نفس الـ IP برمز `429 Too Many Requests`.
  2. أثناء جلسات الفحص والاختبارات التتابعية، يتم استهلاك الـ 100 طلب في ثوانٍ معدودة مما يعطل بقية استدعاءات الـ API.

### خطة المعالجة الهندسية عند التنفيذ:
1. **التقسيم حسب المستخدم المسجل (User-Keyed Rate Limiting)**:
   * الاعتماد على `req.user.userId` للطلبات المصادقة، والـ IP فقط للزوار غير المسجلين.
2. **ربط الـ Limiter بـ Redis مباشرة**:
   * استخدام `rate-limit-redis` ليتم مشاركة العدادات بين جميع عمليات الخادم (Horizontal Cluster Scaling).
3. **تخصيص سقوف ديناميكية حسب نوع المسار**:
   * **مسارات المصادقة الحساسة (`/api/auth/login`)**: 10 محاولات / 15 دقيقة مع تخطي المحاولات الناجحة (`skipSuccessfulRequests: true`).
   * **مسارات القراءة والتصفح (`/api/goals`, `/api/tasks`)**: 500 طلب / 15 دقيقة.
   * **مسارات الذكاء الاصطناعي (`/api/ai/message`)**: مقيدة برصيد الباقة اليومي.

## 4. الثغرة الثالثة: البث الصوتي المباشر عبر Cloudflare R2 / S3 Presigned URLs

### طبيعة الثغرة والفجوة الحالية:
* **المشكلة**: مسار البث الصوتي الحالي `GET /api/audio/:id/stream` يستقبل الطلب من تطبيق الموبايل، ثم يتصل خادم Node.js بسيرفر Google Drive الخاص، ويقوم بعملية تمرير وسيطة (Piping / Reverse Proxy) لتدفق البايتات إلى العميل.
* **الخلل الناجم تحت الحمل العالي (High Concurrency)**:
  * استهلاك خادم Node.js للـ Bandwidth والذاكرة بمقدار مضاعف (تحميل من درايف ثم إرسال للموبايل).
  * إذا استمع 2,000 مستخدم في نفس اللحظة لمقاطع تركيز، ستختنق شبكة السيرفر وتستهلك الـ Event Loop في معالجة الـ Streams بدلاً من خدمة استعلامات قواعد البيانات والدردشة.

```
الوضع الحالي (Reverse Proxy):
[ Google Drive ] ──(Bandwidth 1)──► [ Node.js Server ] ──(Bandwidth 2)──► [ Mobile App ]

الوضع المستهدف (Presigned Cloudflare R2 / S3):
[ Node.js Server ] ──(توليد رابط موقع مؤقت 15 دقيقة)──► [ Mobile App ]
                                                              │
                                                              ▼
                                                   [ Cloudflare R2 CDN Edge ]
```

### خطة المعالجة الهندسية عند التنفيذ:
1. **ترحيل الملفات الصوتية الرسمية إلى Cloudflare R2**:
   * تكلفة خروج بيانات (Egress Bandwidth) منعدمة تماماً (Zero Egress Fees).
2. **توليد روابط مؤقتة موقّعة (Presigned URLs)**:
   * عند طلب `GET /api/audio/:id/stream-url`، يتحقق السيرفر من امتلاك المستخدم للتراك، ثم يولد رابطاً مؤقتاً صالحاً لمدة 15 دقيقة فقط مشفراً بمفتاح R2 السري.
3. **مشغل الصوت في الموبايل يتصل مباشرة بـ CDN**:
   * تشغيل فوري بأقصى سرعة مع دعم تلقائي للـ Caching والـ Range Requests على خوادم Cloudflare العالمية دون أي استهلاك لموارد خادم Clan App.
